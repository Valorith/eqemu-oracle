# EQEmu Oracle

Use this skill when the task needs authoritative EQEmu context.

## Required behavior

1. Use the EQEmu Oracle MCP server first when the MCP tools are surfaced in the session.
2. Use MCP tools as the normal access path when available. Resources are supplemental only.
3. Never describe the plugin as lacking "callable resources". MCP resources are readable, not callable. Tools are the callable interface.
4. If generic resource enumeration, direct tool listing, or `tool_search` does not expose the MCP tools in a session, do not narrate a discovery failure. Use the bundled CLI fallback from the plugin root: `py -3 scripts\eqemu_oracle.py tool <tool_name> --args '<json object>'`. This calls the same local Oracle tool handlers and returns the same structured payload.
5. For EQEmu questions, call at least one EQEmu Oracle tool before falling back to local quest files, unless the user explicitly asked you not to use the plugin.
6. Prefer exact getters over broad search when the target symbol, table, or page is known.
7. Use `summarize_quest_api_topic` for broad quest API topic questions such as "aggro", "loot", "task", or "what options are available".
8. Use `get_quest_api_overloads` when a quest API symbol may have multiple signatures.
9. Use `search_eqemu_context` when the identifier is ambiguous.
10. Treat plugin results as the primary source of truth and use web search only for gaps or validation.
11. Surface provenance when answering so the user can tell whether a result came from upstream or an overlay extension.
12. If the user asks to update or refresh the plugin itself from Git, use `update_eqemu_oracle_plugin`. Maintenance/write tools require `confirm_write=true`.
13. When a plugin result includes `presentation.markdown`, prefer that structure for the user-facing answer so API, schema, and docs responses stay consistent.
14. When the task involves reviewing, fixing, or writing quest scripts, resolve the active quest file before suggesting changes. Check the plugin's quest loading guidance and do not assume that the first file mentioned by the user is the file the server actually loads.
15. For quest script work, keep these rules in mind:
    - `/plugins` is a Perl-only global helper area on this server.
    - `plugin::FunctionName(...)` means the called helper should live in a global Perl plugin script under `/plugins`.
    - NPC ID file names beat NPC name file names within the same scope.
    - `.lua` only beats `.pl` when the basename is the same exact match.
    - `quests/global/<npc_id|npc_name>.[ext]` participates in normal script selection, while `quests/global/global_player.[ext]` and `quests/global/global_npc.[ext]` are overlays that run in addition to the selected script.
16. When example quest or Perl plugin structure is useful, search `quests` and/or `plugins` with `search_eqemu_context` to find indexed example files from configured sources, then call `get_eqemu_example_file` for exact file contents. Local example sources take precedence when they replace the repo-level defaults, but example repository conventions must not override the active server layout or official EQEmu loading rules.
17. For any task that involves active server files, remote quest/plugin files, or "my server" code without a local path, call `list_eqemu_server_ftp_profiles` early to discover whether FTP/FTPS access is configured. If no profiles exist, call `get_eqemu_server_ftp_onboarding` and direct the user to the local setup flow. Do not ask the user to paste FTP passwords into chat.
18. If exactly one FTP/FTPS profile is configured, use it for safe read/download work unless the user named a different profile. If multiple profiles are configured and the target is ambiguous, ask which profile to use before staging or writing remote files. Always inspect the profile's `read_only` value before considering any FTP write action.
19. Before remote FTP work, build fresh situational awareness with `map_eqemu_server_ftp_layout` unless the user supplied an exact remote path and the current task already has a fresh map/list result for that path. Use the narrowest useful scope (`overview`, `quests`, `zone`, `plugins`, `logs`, `binaries`, `global`, `global-items`, or `global-spells`) so discovery is efficient and on demand. Do not guess remote file paths when a safe map can identify what is actually available.
20. The mapper is read-only and understands this EQEmu server layout: `/binaries` contains binary package folders, `/logs/crashes` and `/logs/zone` contain text crash reports, `/logs/*.log` and `/logs/zone/*.log` may contain runtime logs, `/plugins` contains top-level Perl plugin scripts, and `/quests` contains zone folders plus `/quests/global`, `/quests/global/items`, and `/quests/global/spells`.
21. Use the remote mapper's classifications when selecting scripts: NPC quest files may be named by NPC name or numeric NPC type id, and when `.lua` and `.pl` files share the same basename in the same script directory, the Lua script is the active one and the Perl file is shadowed.
22. Remote FTP/FTPS mapping, listing, connection testing, write-history review, undo preview, and staging are safe actions. Use `test_eqemu_server_ftp_connection`, `map_eqemu_server_ftp_layout`, `list_eqemu_server_ftp_files`, and `stage_eqemu_server_ftp_file` when reviewing remote quest or plugin files. Prefer staging the active remote file from the fresh map before proposing edits that depend on server-specific code.
23. If the Nexus CLI skill/helper is setup and available, use it situationally as a supporting signal source when it is likely to add value to the current task, especially to check the Webhook Inbox for script errors, failed webhooks, and crash-report payloads that may identify an affected script or reproduce context. Do not make Nexus a mandatory dependency, do not run broad inbox queries for unrelated work, and do not expose raw sensitive webhook payloads.
24. When the user asks to use EQEmu Oracle to fix a script error on a configured test server, follow this workflow: map/list enough of the FTP layout to identify the active affected script; optionally check Nexus Webhook Inbox evidence if available and value-added; stage/download that exact script into a local task working area; review the staged file and make the needed local edits; summarize the proposed change and ask the user to review and explicitly approve uploading the fixed file back to the test server. Do not upload during the analysis/editing step. After approval, prefer `run_eqemu_server_ftp_upload_session` for the overwrite so read-only mode is restored in tool cleanup; otherwise use the guarded upload flow. Then stage or otherwise read the remote file again to validate the fix is in place and report the write-history operation id.
25. After a script error fix is uploaded through EQEmu Oracle FTP, if the Nexus CLI is setup and available, ask the user whether they want a new Test Manager change record created through Nexus. Only create it after explicit user approval. If approved, keep the Change Description concise and tester-facing: describe the player-visible issue, what changed, and what should be tested in plain language; avoid raw stack traces or developer-heavy details unless the user asks for them.
26. If read-only mode is enabled and the requested FTP task cannot be completed in read-only mode, tell the user the FTP profile is in read-only mode and ask for explicit permission to exit read-only mode for that specific task. Do not disable read-only mode until the user gives that explicit permission and the exact mode-change confirmation fields can be supplied. If read-only mode was disabled for an approved FTP write task, re-enable read-only mode automatically as cleanup before finishing the task, even if the write task fails partway through; report the final read-only state to the user.
27. Treat `trust_eqemu_server_ftp_certificate` as a user-commanded local trust change only. Use it to preview a self-signed or hostname-mismatched FTPS certificate fingerprint, and only confirm after explicit user instruction with exact `confirm_sha256`. Pinned FTPS keeps TLS encrypted and refuses to send credentials if the certificate fingerprint changes.
28. Treat `set_eqemu_server_ftp_read_only_mode` as explicit-only for leaving read-only mode. Never infer consent from a broader task, and never disable read-only mode unless the user explicitly instructs that exact mode change. Re-enabling read-only mode is allowed as automatic safety cleanup after an approved write task where you disabled it for that same task. Use the preview first, then only confirm with `confirm_mode_change=true`, exact `confirm_profile`, and exact `confirm_read_only_mode`.
29. Treat `upload_eqemu_server_ftp_file` and `run_eqemu_server_ftp_upload_session` as high risk. Use them only after explicit user approval. Confirmed overwrite calls must include `confirm_write=true`, the exact `confirm_remote_path`, and the exact `confirm_remote_sha256` for the staged or previewed remote file; this prevents overwriting if the remote file changed after review. Creating a new remote file also requires explicit `allow_create=true`; never set it unless the user asked to create that exact path. Prefer `run_eqemu_server_ftp_upload_session` for approved uploads because it temporarily opens write access if needed and re-enables read-only mode in cleanup. Upload creates a local restore point, verifies the remote file after write, and returns a write-history operation id plus `write_audit`. After any successful write, report the operation id, remote path, before/after SHA-256 values, final read-only mode, and undo availability from `write_audit`.
30. Treat `delete_eqemu_server_ftp_file` as high risk. It must only be used after explicit user approval, and the confirmed call must include `confirm_delete=true`, the exact `confirm_remote_path`, and exact `confirm_remote_sha256` returned by preview. Delete is blocked when the profile's `read_only` mode is true. Confirmed delete creates a local restore point, verifies the file is gone, and returns a write-history operation id that can be undone.
31. Use `list_eqemu_server_ftp_write_history` and `preview_eqemu_server_ftp_undo` to inspect recent remote writes and undo options. Treat `undo_eqemu_server_ftp_write` as high risk; it must only run after explicit user approval with `confirm_write=true` and the exact `confirm_operation_id`. Undo is blocked when the profile's `read_only` mode is true. Undo can restore overwritten/deleted files or remove a file created by guarded upload. After a successful undo, tell the user the new undo operation id. Remote rename, chmod, and directory-removal actions are not available.
32. Use `garbage_collect_eqemu_server_ftp_write_history` to preview local undo retention cleanup when history reports garbage collection is needed. Applying GC deletes only local restore-point files beyond retention or orphaned under the profile backup directory; it never touches remote server files, but it still requires explicit user approval with `confirm_write=true` because it reduces available undo history. GC apply is blocked when the profile's `read_only` mode is true.

## CLI Fallback Examples

Run these from the installed EQEmu Oracle plugin root when MCP tools are not directly exposed:

- `py -3 scripts\eqemu_oracle.py tool search_eqemu_context --args '{"query":"spawn2","domains":["schema"],"limit":5}'`
- `py -3 scripts\eqemu_oracle.py tool get_db_table --args '{"table_name":"spawn2"}'`
- `py -3 scripts\eqemu_oracle.py tool get_quest_api_entry --args '{"language":"perl","kind":"method","name":"say"}'`
- `py -3 scripts\eqemu_oracle.py tool get_doc_page --args '{"path_or_slug":"schema/spawns/spawn2"}'`

For remote server setup, use `py -3 scripts\eqemu_oracle.py remote setup` from the installed plugin root.
